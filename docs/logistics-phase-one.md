# Phase 1: RTD to delivery

Open **Flow → Logistics · RTD to Delivery** (`/logistics`). The register shows the five stages and overdue shipments. The production/source team's Ready to Dispatch confirmation is the entry point. It can be entered using a linked Zoho document or a manual Sales/DC/TO/PO reference. Importing a document does not mark it RTD.

1. **Receive RTD:** select the site, source, provider, journey and ready item quantities. Load a Zoho sales order for D2C or an invoice for inland. Refresh the selected document to fetch line items and shipping address using the read-only Zoho client. Related packages are displayed when an order link is available. A confirmed manual reference remains possible for documents outside the Zoho sales import.
2. **Assign:** use the existing approved Transporter Master and add vehicle types in the logistics screen. D2C offers Express/Premium. Inland supports all specified modes, vehicle type, transporter quotes, price/rank comparison and reasons for a non-leading choice. Road modes require vehicle and driver contact. Capture agreed freight and the transporter's EDD.
3. **Dispatch and track:** record actual dispatch, in-transit EDD changes with reasons, arrival, then delivery. Every transition validates stage, actual-time chronology and version. The activity history identifies the actor and reason. An optional link to an existing outward shipment requires its physical gate dispatch first.
4. **Finish:** record loading/unloading/halting/other charges, with reasons and audited voids. Delivery is distinct from POD completeness. Upload private POD/E-Way Bill/reference files; optionally save Google Maps/POC and revenue for cost comparison. Export the filtered register to CSV.

This module tracks transport and does not write to the stock ledger. Existing Flow inventory and the outward gate remain responsible for stock movements. Zoho credentials, imported records, and the existing operational modules are retained. It does not generate GST documents, create stock transactions, or assume an unprovided machine-to-machine manufacturing event contract.

Existing permissions apply: order creation or production release can mark RTD; order view is required to access Zoho sources; dispatch manages quotes/plan/departure/charges; delivery manages arrival/delivery/POD. Site restrictions apply to the register, actions and attachments. The standalone authenticated `POST /logistics/rtd` intake delegates to `LogisticsService::markRtd()` for future internal handoff integration.

The migration is additive. It adds the logistics tables, an atomic sequence retaining existing Flow shipment-number formatting, and a composite index for the Zoho date list. Legacy shipment loading and delivery now enforce legal state, order association and completion of every loaded order. Legacy unit selection and in-transit deliveries use bounded lists; the logistics export streams batches.

Validation used isolated databases and matching dependencies: 15 targeted tests / 136 assertions passed, including both full paths, source branches, permission/version checks, no additional stock posting, and the four previously reproduced legacy delivery/dispatch defects. The 41-test existing outward/inventory/import comparison reproduced the same 36 passes and five pre-existing InventoryFlow failures/errors, with no new failing tests in that suite. Existing test-handler cleanup warnings remain. This is functional validation and query-plan improvement, not a system-wide load certification.
